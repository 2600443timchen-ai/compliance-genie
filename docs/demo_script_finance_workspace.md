## Part 1｜案件處置工作台（單案深度分析）

### 1-1 開場：介紹三種輸入方式（不點擊，純講解）

畫面停在空白搜尋頁，依序指向三個區塊：

| 步驟 | 對應 UI 元素 | 口白重點 |
|---|---|---|
| ① 搜尋欄位 | 頂部 `輸入案件編號 (如 C001) 或關鍵字...` 搜尋框 + 搜尋鈕 | 「使用者可以直接搜尋既有案件編號，或用關鍵字如『投資型』『醫療險』『告知義務』做模糊查找。」 |
| ② 匯入欄位 | 左側 `拖曳案件 PDF/CSV 至此上傳` 拖放區 | 「如果案件資料已經是 PDF 或 CSV，可以直接拖曳或點擊上傳，系統會自動解析建檔。」 |
| ③ 直接輸入欄位 | `或 手動填寫自訂案件` 表單（申請人姓名／案件類型／爭議要點／爭議金額） | 「若沒有現成檔案，也能手動輸入基本資料，點『建立並載入案件』直接生成一個新案件。」 |

> 講解節奏建議：每個方式 10–15 秒，滑鼠 hover 對應區塊即可，不需真的送出。

### 1-2 正式進入流程：載入 C001 並啟動深度分析

1. 點擊快速試用標籤 **`C001 (信用卡 OTP 詐騙)`**
   - 口白：「我們直接用一個真實案例情境：信用卡 OTP 詐騙爭議。」
   - 左側 `案件資訊` 卡片會帶出案件類型、爭議項目、爭議金額、建立/更新日期。
2. 點擊左側卡片底部 **`啟動 AI 深度分析`** 按鈕（`askAiToAnalyzeCase()`）
   - 口白：「這一鍵會觸發 AI 針對這個案件做完整的財務與監理曝險試算，不是套用固定範本，是即時分析。」
   - 此時可以順帶提一句：分析是呼叫 Gemini 即時運算，畫面上會看到 loading 狀態（`等待 AI 試算...` / `等待 Chat 分析...`），刻意保留這個過程讓觀眾感受「這是即時算出來的，不是預先寫死的 demo 數字」。

### 1-3 資料成功載入後：左→中→右介紹輸出成果

等待分析結果填入後，依序從左到右講解三個欄位：

**① 左欄｜案件資訊 + 財務與監理風險（`case-sidebar`）**
- 建議和解金額區間
- 單案監理曝險評估：法定罰鍰級距、相似裁罰案例區間、本案監理曝險情境、目前最可能區間
- 缺少證據清單
- 💡 金融合規理算依據（AI 給出的判斷邏輯，不是黑箱）
- AI 預測信心指數（如 85%）
- 歷史支撐依據（可點擊連結查看裁罰案例來源）

> 💡 **補充時機點**：講到「缺少證據」這一項時，順勢帶出——
> 「如果案件細節不完整，我們支援直接上傳補充檔案（PDF/CSV/TXT），可以用左側拖放區，也可以用聊天輸入框旁的迴紋針『夾帶上傳案卷』按鈕，上傳後 AI 會重新納入分析。」
> （對應 UI：`attach-btn` 迴紋針圖示，位於聊天輸入框左側）

> 💡 **可選加分點（若評審有問到 session 隔離／重整頁面）**：切到瀏覽器重新整理一次頁面，再點回同一個 C001。口白：「案件與聊天室是一對一綁定的，重整或切換案件再切回來，AI 對話紀錄會原封不動還原，不會跟其他案件或其他人的對話混在一起。」（對應 [analytics_server.py](../analytics_server.py) 的 `get_dashboard_chat`，依案號建立/查找專屬聊天室；沒有寫入權限時會自動退回共用聊天室，不會整段失敗。）

**② 中欄｜AI Chat 對話（`chat-section`）**
- 展示 AI 分析結論的完整對話串（適法性評估、違規紅旗、建議 SOP）
- 可點一次快捷提示 chip，例如「🚩 抓出案件違規紅旗」，示範真人也能追問

**③ 右欄｜參考資料面板（`reference-panel`）**
- ⚖️ 檢索相關法規：AI 自動比對出的相關條文
- 📝 AI 案件爭議要點摘要
- 口白重點：「這兩塊不是關鍵字搜尋結果，是 AI 讀完案件後主動摘要與比對法規，形成一個可追溯的合規依據鏈。」

## Part 2｜交叉分析與洞察儀表板

從頂部切換鈕點擊 **`交叉分析與洞察儀表板`**（NEW 標籤）進入。

### 2-1 資料載入等待期間：介紹儀表板功能

畫面初次進入會顯示「正在連線 Gemini Data API」「載入中…」，這段等待時間正好用來口頭介紹版面：

- **頂部風險摘要區**：風險指數環形圖、正式來源驗證數
- **四張 KPI 卡片**：
  - **新增高風險事件**：依案件資料庫已揭露金額計算 Q3（上四分位數）門檻，達門檻以上計為高風險事件——確定性統計，不是 AI 判斷。
  - **潛在財務曝險**：案件資料庫已揭露涉案金額直接加總，同樣是確定性運算。
  - **SLA 逾期風險**：誠實標示「尚未連接」，因為目前沒有任何已連接來源提供處理期限/承辦人欄位。
  - **待完成法規缺口**：隨機抽樣 10 筆案件，即時請 AI 逐筆判斷缺少的證據或法規依據並加總——卡片會明確標示「抽樣 N 筆案件推估」，不宣稱是全量盤點。
- **重大異常訊號卡**：案件趨勢走勢圖 + 影響範圍/主要缺口/判定信心/外部產業基準
- **正式資料排行榜**：依來源列出排名項目

### 2-2 互動示範：Hover 查看細節 + 點擊喚出 AI 解析

1. 滑鼠移到任一張帶有 `insight-target` 標記的卡片（例如 KPI 卡片、重大異常卡、來源排行項目），**停留約 0.5 秒不點擊**
   - 會彈出 popover 顯示該指標的詳細解釋
   - 口白：「每一個數字背後都可以直接懸停查看，不用跳頁。」
2. **點擊**同一張卡片，popover 會被「釘住」（pinned），停留展開
3. 點擊 popover 內的 **「詢問 AI」按鈕**（`insight-ask`）
   - 系統會自動組出問題：「請解釋『{指標名稱}』為什麼是 {數值}，並告訴主管下一步」
   - 觸發 `askDashboardAssistant()`，即時呼叫 AI 針對這個具體指標做解讀與建議行動
   - 口白：「這不是靜態 tooltip，是把當前指標的上下文直接餵給 AI，讓它像顧問一樣給出下一步建議。」

（可選）點擊「重大異常」卡片下方的 **`深鑽關聯案件 →`**，展開關聯案件明細，呼應第一部分「單案分析」與第二部分「宏觀儀表板」是同一組資料的兩種視角。

## 評審問答準備｜Gemini Data 相關提問

以下鎖定「評審自己就是 Gemini Data 平台方」這個前提，篩掉不需要準備的項目，只留下你們自己該負責、且現在答得出來或答不出來的部分。

### ✅ 現在答得出來（已經修好，可以主動示範）

**Q：多人同時使用、或重新整理頁面，AI 對話會不會互相污染？**
A：「原本是全部使用者共用一個聊天室，我們已經改成每個案件對應一個獨立聊天室，用案號當識別碼。同案件重整或切換回來會回到同一間、還原歷史紀錄；不同案件天生隔離，不會混在一起。」（可現場示範：重整頁面、重新點 C001，對話紀錄還在。）

**Q：如果沒有建立新聊天室的權限呢？**
A：「這支 API 需要跟上傳知識庫一樣的寫入權限。我們有做降級處理：建立失敗時會自動退回原本的共用聊天室，不會整個功能掛掉，只是那個 session 暫時無法獨立隔離。」——**誠實揭露有 fallback，但不用主動示範失敗情境**，除非評審自己測出來才順勢解釋。

**Q：「新增高風險事件」這張卡的「高風險」是怎麼定義的？**
A：「我們用案件資料庫裡已揭露的爭議金額，計算 Q3（第三四分位數／上四分位數），金額落在 Q3 以上的案件計為高風險事件。這是統計上常見的離群值判斷法，用意是找出金額明顯偏高、值得優先關注的案件，不是正式的法規風險分級——如果貴單位有明確的風險分級標準，我們可以直接換成那套規則。」（這是真的在後端算出來的分位數，不是隨口說的方法論；卡片下方 hover 會顯示實際門檻金額，可以當場點開驗證。）

**Q：「待完成法規缺口」這個數字準嗎？**
A：「這是抽樣估算，不是全量盤點。我們每次隨機抽 10 筆案件，即時請 AI 逐筆判斷缺少的證據或法規依據，加總成這個數字，卡片下方也會標『抽樣 N 筆案件推估』。全量案件的深度分析我們有另外做（就是剛剛示範的單案深度分析，會產出 missing_evidence 缺口清單），但要對全部案件都跑一次還沒有批次機制，現在的儀表板數字只能當趨勢參考，不能當成正式盤點結果。」

> ⚠️ **實測發現**：用真實 token 跑過一次，AI 對案件資料庫裡的已結案案件（已有 outcome/Regulation/改善措施等完整欄位）大多判斷 gap_count = 0——因為這些是已經走完評議流程的結案案件，資料本來就相對完整。也就是說demo當天這張卡很可能常態顯示「0 項」，這是誠實的結果，不是功能沒作用。如果評審問「怎麼都是 0」，可以直接照實回答：「這批抽樣剛好都是已結案、資料完整的案件；缺口分析對還在處理中、資料不全的案件才會有意義。」不要因為數字是 0 就慌，那反而證明系統沒有為了做出效果而灌水。

### ⚠️ 現在答不出來（老實承認，不要硬凹）

**Q：上傳的 PDF/CSV 案卷資料如何被解析並注入 AI context？**
A（可以講的部分）：「檔案上傳後，如果雲端知識庫有寫入權限，會走 signed URL 上傳並註冊進 Vector Knowledge 做 RAG；如果權限不足，我們有一個本地降級路徑，會直接在後端把 PDF 用 pypdf 擷取純文字、CSV/TXT 直接讀取，當次對話用這份文字當上下文，但不會真的存進雲端知識庫。」
（答不出來的部分，直接承認）：「掃描型 PDF（沒有文字層）目前這條本地路徑會直接判定失敗，沒有做 OCR；這塊確實還沒解決，如果評審上傳的是掃描檔，我們會如實告知目前不支援，而不是假裝有處理。」

**Q：上傳功能一直跳權限不足，原因排查到哪裡？**
A：「我們有針對這個路徑寫了單元測試（覆蓋簽發 URL、寫入知識庫、權限降級三個分支），測試本身是通過的，但實際串接貴平台的 tenant 時仍會拿到 401/403，研判是這組 API 帳號目前沒有 `source:write` 權限，需要貴平台這邊確認授權範圍——這部分老實說要請你們協助排查，不是我們程式邏輯的問題。」

### 🚨 展示當天的硬性限制（務必遵守）

**千萬不要在展示過程中重啟 `analytics_server.py`。** 案件對應聊天室的記憶體目前是活在伺服器行程裡（`_case_chat_map`），重整瀏覽器頁面沒事，但只要後端程序重啟一次，所有案件都會被視為「第一次載入」，重新建立新聊天室——舊的聊天室仍然存在於 Gemini 那邊，只是我們自己也找不回來了，History 會變成空的。開場前啟動一次伺服器，全程不要關閉那個終端機視窗。

### 🙅 不用準備（評審系統自己的責任，禮貌帶過即可）

- Gemini API 持續超時的重試/降級策略
- 上游資料一致性、`/chat/list` 回應延遲
- Tenant 帳號的權限模型設計是否合理

被問到時一句話帶過即可：「這段是貴平台 API 本身的行為，我們這邊已經做了合理的重試與錯誤訊息呈現，更深層的穩定性要麻煩你們那邊確認。」不需要辯解，也不用堆理由，講完就換下一題。
