# 金融爭議分析：資料結構與需求數據規格表

目的：針對「場景與邏輯漏洞剖析（Operational Gaps & Root Cause Flaws）」落地資料底座，提供資料庫工程師可直接實作的欄位需求與設計理由。

## 一、核心資料表（最小可行）

| 資料表 | 主要欄位（建議型別） | 需要什麼 | 為什麼需要 |
|---|---|---|---|
| cases | case_id (PK, varchar), received_at (date), closed_at (date, nullable), category (varchar), product_code (varchar), product_version (varchar), channel_code (varchar), segment_code (varchar), disputed_amount (decimal), exposure_count (int), outcome_code (varchar), outcome_weight (decimal), source_system (varchar), ingested_at (timestamp) | 案件主檔與可計算的分母/分子欄位 | 沒有統一主檔就無法穩定計算成立等值風險率，也無法做跨產品、跨通路、跨版本比較 |
| case_regulations | case_id (FK), regulation_id (FK), citation_confidence (decimal), citation_source (varchar), is_primary (boolean) | 案件與法規多對多映射 | 若法規只塞在字串欄位，無法做法規熱點聚合、覆蓋率計算與追溯 |
| regulations | regulation_id (PK), law_name (varchar), article_no (varchar), clause_no (varchar), title (varchar), effective_date (date), retired_date (date, nullable) | 法規維度標準化 | 法條版本會變動，需可追蹤生效時間，避免錯用過期法規做統計 |
| case_violations | case_id (FK), violation_type_id (FK), severity_score (decimal), detected_by (varchar), detection_confidence (decimal), created_at (timestamp) | 控制缺口（違規態樣）明細 | Root cause 分析需要可拆解到 violation 層，否則只能做表面摘要 |
| violation_types | violation_type_id (PK), violation_code (varchar), violation_name (varchar), risk_domain (varchar), active_flag (boolean) | 違規字典 | 沒有標準字典會造成同義詞分裂，導致統計失真 |
| case_evidence | evidence_id (PK), case_id (FK), evidence_type (varchar), evidence_ref (varchar), evidence_text_hash (varchar), evidence_time (timestamp, nullable), source_uri (varchar), traceability_score (decimal) | 證據索引與可追溯性 | 沒有 evidence 索引就無法驗證圖譜連結、也無法支持稽核抽查 |
| case_event_timeline | event_id (PK), case_id (FK), event_type (varchar), event_time (timestamp), actor_role (varchar), payload_json (json) | 案件流程事件流 | 你要做突發暴增根因分析，不保留事件流就只能人工回放 |
| model_outputs (optional) | output_id (PK), case_id (FK, nullable), batch_id (varchar), model_name (varchar), prompt_hash (varchar), output_type (varchar), output_json (json), generated_at (timestamp), verified_flag (boolean) | LLM 產出留痕 | AI 只能當輔助；必須可留痕與驗證，避免不可稽核的黑箱結論 |

## 二、關鍵需求數據（指標計算必備）

| 指標/分析需求 | 需要的欄位 | 計算口徑 | 為什麼需要 |
|---|---|---|---|
| 成立等值風險率（每萬曝險） | outcome_weight, exposure_count | rate = sum(outcome_weight) / sum(exposure_count) * 10000 | 風管需要統一風險密度指標，避免只看案件數 |
| 高風險商品排序 | product_code, product_version, outcome_weight, exposure_count, disputed_amount | 先算風險率，再以金額與樣本量做 tie-break | 避免小樣本高波動誤導資源分配 |
| 法規熱點 | regulation_id, case_id, received_at | 統計法規引用量、成立量、爭議金額 | 支撐合規政策調整與訓練重點排序 |
| 控制缺口 Top N | violation_type_id, severity_score, case_id | 按頻次與嚴重度雙軸排序 | 僅看頻次會低估高損害低頻事件 |
| 證據覆蓋率 | case_id, evidence_id, traceability_score | traced_cases / total_cases；可加權可信度 | 沒有覆蓋率就無法判斷結論可稽核性 |
| 突發暴增根因（RCA） | case_event_timeline.*, channel_code, product_version, violation_type_id | 比較事件前後的變化（通路/版本/違規態樣） | 不保留事件與版本就找不到 trigger point |

## 三、資料品質與治理規則（必做）

| 規則 | 實作建議 | 為什麼需要 |
|---|---|---|
| 主鍵與唯一性 | case_id 全域唯一；外鍵完整約束 | 防止重複案件與孤兒資料 |
| 時間欄位可用性 | received_at 必填；event_time 必填 | 沒有可用時間欄位無法做異常偵測與 RCA |
| 代碼表治理 | category/product/channel/segment 用 code table | 降低自由文字導致的聚合失真 |
| 數值合理性檢查 | exposure_count > 0；disputed_amount >= 0 | 避免分母為 0 與負值污染指標 |
| 稽核留痕 | 所有更新寫入 audit log（who/when/what） | 金融場景必須可追責與可還原 |
| 模型輸出隔離 | model_outputs 與 facts 分層儲存 | 防止 AI 文字污染事實資料層 |

## 四、最低交付清單（給資料庫工程師）

| 優先級 | 交付項目 | 驗收標準 |
|---|---|---|
| P0 | 建立 cases、regulations、case_regulations、case_violations、case_evidence、case_event_timeline | 能支援單批次（>= 10k 案件）聚合查詢，且關聯完整 |
| P0 | 建立代碼表與資料驗證規則 | 匯入錯誤資料可被攔截並回報明確錯誤訊息 |
| P1 | 建立指標視圖（materialized view） | 1 秒內返回常用 KPI（按 category/product/segment） |
| P1 | 建立 evidence 覆蓋率與追溯性報表 | 可輸出 traced_cases/total_cases 與明細清單 |
| P2 | 建立 model_outputs 留痕與驗證旗標 | AI 輸出可追溯到 prompt 與版本，且可被標記為未驗證 |

## 五、補充說明

- 原則：事實資料（案件、法規、證據、事件）與模型敘事（LLM output）必須分層。
- 統計口徑：先定義指標口徑，再開發前端視覺化，避免 UI 先行導致數據失真。
- 稽核觀點：任何管理層看板都必須能回鑽到 case_id 與 evidence_id。
